# Publishing high5rotate on Google Play

This is a guided release checklist, not a record of a completed Play submission. Policy links were checked on 8 September 2026. Start with internal testing; production comes after testing on real phones and completing the Console requirements.

## 1. Find or create your developer account

Open [Play Console](https://play.google.com/console) with each Google account you might have used. An existing developer account shows a dashboard/account selector. A registration screen means that signed-in account still needs registration or access to someone else's developer account.

If needed, follow Google's registration and identity-verification flow. Registration currently costs US$25 once. Choose personal if publishing for yourself; choose organization only for a real organization whose verification information you can provide. Do not share your password or identity documents in the repository or chat. [Google's registration guide](https://support.google.com/googleplay/android-developer/answer/6112435?hl=en)

Still needed from the publisher:

- Public developer name and a public support email address.
- Developer account verification and any requested device verification.
- Decision on free/paid distribution and countries. The current app has no purchases or ads; free is the proposed starting point. Confirm this before creating the listing because a published free app cannot later become paid.
- Whether to grant an open-source license. Public source availability alone does not grant a license; none has been selected automatically.

## 2. Create the app entry

In Play Console choose **Create app**, use **high5rotate**, English (United States), and **App**. Decide free/paid before proceeding. The Android package ID is `org.toitlang.wcsrotate`, retained so existing installations can be updated. Display name and repository name are `high5rotate`. The package ID becomes permanent for this Play app.

The project targets Android 16 / API 36, meeting the currently documented target for new submissions. [Target API requirements](https://developer.android.com/google/play/requirements/target-sdk)

## 3. Create and protect the upload key

Use Play App Signing with Google's generated app-signing key. The local upload key signs bundles submitted to Play; keep its keystore and passwords backed up privately. Do not use the debug key for publication. [Android signing guide](https://developer.android.com/studio/publish/app-signing)

Run locally in a private terminal, selecting a location outside this repository:

```sh
keytool -genkeypair -v -keystore /absolute/private/path/high5rotate-upload.jks \
  -alias high5rotate-upload -keyalg RSA -keysize 2048 -validity 10000
```

The tool prompts for your password and certificate details. Do not paste the password into chat. Then set `HIGH5ROTATE_KEYSTORE` to the absolute path and `HIGH5ROTATE_KEY_ALIAS` to `high5rotate-upload`. Set `HIGH5ROTATE_STORE_PASSWORD` and `HIGH5ROTATE_KEY_PASSWORD` privately in your local environment, without putting literal secrets in command history. For a PKCS12 keystore, the key password normally matches the store password.

```sh
./gradlew testDebugUnitTest lintDebug bundleRelease
jarsigner -verify app/build/outputs/bundle/release/app-release.aab
```

With all four environment variables, Gradle signs the release. With none, it builds an **unsigned** bundle for validation; that bundle cannot be submitted to Play. Partial signing configuration fails explicitly. No upload key has been generated by this preparation.

The artifact is `app/build/outputs/bundle/release/app-release.aab`. Before every later upload, increment `versionCode` in `app/build.gradle.kts`; version 1 is reserved for the first upload. CI artifacts are unsigned release bundles and debug APKs, not production releases.

## 4. Complete the store listing

Copy `title.txt`, `short-description.txt`, and `full-description.txt` from this directory. Proposed category: **Tools**. Upload `assets/icon.png` (512 × 512) and `assets/feature-graphic.png` (1024 × 500). The feature-graphic alt text is: “high5rotate: partner rotation cues for dance classes.”

Capture at least two genuine phone screenshots from the final app, such as an active song countdown and the sound/timing controls. Prefer 1080 × 1920 portrait; don't substitute mockups for actual app screenshots. Use a track you have permission to show. Screenshots and the foreground-service video still need to be recorded on a working device. [Google's asset requirements](https://support.google.com/googleplay/android-developer/answer/9866151?hl=en)

Privacy-policy URL after GitHub Pages is enabled: `https://floitsch.github.io/high5rotate/privacy.html`. Verify that it opens publicly without signing in before submitting. The policy is also bundled in the app. Fill in the chosen public support email in Play Console. The public project page is `https://github.com/floitsch/high5rotate`.

## 5. Complete App content

Use [app-content.md](app-content.md) as a draft for the Console forms. Review each answer against the actual shipped build and your distribution choices. Complete privacy, Data safety, ads, app access, target audience, content rating, and the foreground-service declaration. Record the demonstration video before sending the app for review.

## 6. Upload to internal testing

Open **Testing → Internal testing**, create a release, enroll in Play App Signing if prompted, upload the signed AAB, and use `release-notes.txt`. Add your Google account as a tester and open the opt-in link on the phone. A locally installed debug APK uses a different signing key; you may need to uninstall that copy before installing the Play build, which clears its settings. Re-enable media access and the battery exemption after installing if needed.

Run [testing.md](testing.md) on the Play-installed build with the actual classroom phone and speaker. Fix failures before broader testing. Internal sharing is not the required closed test for new personal accounts.

## 7. Closed testing and production

Personal accounts created after 13 November 2023 currently need at least **12 testers opted in continuously for 14 days** in a closed test before applying for production access. Recruit actual testers who will exercise the app and report problems. Keep notes on devices, feedback, fixes, and what was tested; the production-access application asks about testing and readiness. Existing or organization accounts can have different requirements shown in their Console. [Google's testing requirements](https://support.google.com/googleplay/android-developer/answer/14151465?hl=en)

After any required production-access approval, create a production release, choose countries, review all declarations and the pre-launch report, and submit. Google review and policy acceptance are still required; neither a successful build nor GitHub publication means the app is approved on Play.
